# Judge Calibration: Dataset Methodology

`evals/judge_calibration/items.jsonl` has 30 items: 10 scenarios x 3 variants each
(good / subtly_wrong / clearly_bad).

## How the items were built

No live OpenAI API key was available while building this dataset, so items were **not**
generated by running the real agent. Instead, each scenario's "good" response was hand-written
to satisfy its rubric criteria, then perturbed into:

- a **subtly wrong** variant: wrong tone, wrong time/day, a missing required detail, or a
  hallucinated fact not supported by the email -- one subtype per scenario, covering all four
  subtypes across the set.
- a **clearly bad** variant: ignores the request, uses the wrong tool entirely, or is rude/
  dismissive.

8 of the 10 scenarios reuse emails already in the course's
`src/email_assistant/eval/email_dataset.py` (marked `"source": "adapted_from_course_dataset"`
in each item); 2 are original (`"source": "original"`). The per-item `rubric_criteria` field
is new (written for this calibration exercise), modeled on the style of the course's existing
`response_criteria_*` bullets.

This is "controlled perturbation," one of the two methods the project plan called for (the
other being live agent generation, which would require a real API key -- see the README's
Quickstart for how to switch to that mode).

## Anti-anchoring

Each item also carries a `quality_tier_intent` field (`good`/`subtly_wrong`/`clearly_bad`) and,
for subtly-wrong items, a `subtly_wrong_subtype`. These are **design metadata describing our
intent when constructing the item, not a ground-truth label**. The labeling CLI
(`evals/judge_calibration/label.py`) does not show them to the human labeler, and shuffles
item order, so the human's pass/fail judgment isn't anchored by which bucket we built the item
for. The real label is whatever the human says; `quality_tier_intent` is only used after the
fact as a sanity check (e.g., "did items we designed as clearly_bad in fact get failed more
often by the human?").
